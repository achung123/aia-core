### MEDIUM

#### [M-1] Namespace-import escape hatch in `no-equity-in-player` rule
- **Location:** [frontend/eslint-rules/no-equity-in-player.js](../../../frontend/eslint-rules/no-equity-in-player.js#L47-L62) (`create(context).check`)
- **Category:** rule coverage / static-analysis gap
- **Description:** The rule only inspects `ImportSpecifier` and `ImportDefaultSpecifier`. A `ImportNamespaceSpecifier` — `import * as client from '../api/client'; client.fetchEquity()` — is not flagged. Scott verified end-to-end by placing a probe file under `src/player/__probe.tsx`: named import triggers the rule; namespace import with subsequent `.fetchEquity()` member access does not. Because `fetchEquity` is a named export of `frontend/src/api/client.ts`, a single namespace import rehydrates full access with zero lint signal. This is the exact layer-3 defense the spec calls for, with a real hole.
- **Recommended fix:** either (a) add an `ImportNamespaceSpecifier` branch that flags the import and asks reviewers to audit uses, or (b) move to a two-pass rule: flag any namespace import of `../api/client`/`../scenes3d/data/useEquityQuery`/`../poker/evaluator` and any `MemberExpression` on that local binding whose `property.name ∈ FORBIDDEN_NAMES`. Add a matching RuleTester case.

#### [M-2] AC-4(a) — opponent-card-face-up lockout verified only via prop threading, not DOM
- **Location:** [frontend/test/pages/TableView.test.tsx](../../../frontend/test/pages/TableView.test.tsx) — `describe('TableView — consumer lockout integration (AC-4)')` (~L285–L325)
- **Category:** test fidelity / spec literalness
- **Description:** AC-4(a) is worded as `screen.queryAllByTestId('card-face-up').filter(c => c.dataset.ownerSeat !== viewerSeat)` has length 0 until `phase === 'showdown'`. Hank's rewrite spy-mocks `<PokerTable>` to a `<div data-testid="poker-table" />` and asserts `props.viewer` and `props.equityOverlay` instead. The inline comment explicitly acknowledges the deviation and delegates the DOM-level check to T-025/T-026. This is the Cycle 27 L-3 carry-forward's *intent* correctly satisfied (the consumer does thread the right props), but it is strictly weaker than the spec wording: any player-mode bug that manifests only when `<PokerTable>`'s internals render (e.g. a future regression in `canSee()` that still accepts the right `viewer` prop) is now solely a T-025/T-026 concern and cannot be caught at the route boundary. Defensible, but should be recorded.
- **Recommended fix:** either (a) keep the current spy-based structure and add one un-mocked end-to-end render with a minimal JSDOM-compatible `<PokerTable>` stub that renders `data-testid="card-face-up"` elements driven by `canSee()`, or (b) accept the trade as a spec refinement and update tasks.md AC-4 to reflect the delegation. Option (a) is lower-risk.

#### [M-3] AC-4(b) — MSW not used; zero-`/equity` proved via `vi.mock('../../src/api/client.ts')`
- **Location:** [frontend/test/pages/TableView.test.tsx](../../../frontend/test/pages/TableView.test.tsx) — `it('fires zero /equity fetches across preflop → showdown lifecycle')`
- **Category:** test fidelity
- **Description:** AC-4(b) names "MSW-captured network log contains zero calls to `/equity`". The suite uses `vi.mock('../../src/api/client.ts', () => ({ fetchEquity: vi.fn(), ... }))` and asserts `fetchEquity` was not called. Combined with the ESLint rule and the runtime gates in `<PokerTable>`, the assertion is adequate as a regression net — but it is strictly tautological for *this* route today: `fetchEquity` is never imported by `TableView.tsx` or anything in its tree, so the assertion also passes for a tree that accidentally imported equity and never called it. A true network-layer observer (MSW or `vi.spyOn(globalThis, 'fetch')`) would be stronger.
- **Recommended fix:** add a `fetch` / `XMLHttpRequest` spy at the global layer that asserts no request URL contains `/equity` during the five-phase loop. Keep the `fetchEquity` mock as a redundant signal.

### LOW

#### [L-1] `useEffect` + `react-hooks/set-state-in-effect` disable is correctly scoped
- **Location:** [frontend/src/pages/TableView.tsx](../../../frontend/src/pages/TableView.tsx#L63-L78)
- **Category:** design / lint-suppression audit
- **Description:** User explicitly asked whether this disable masks a real bug. It does not. The effect synchronizes `scrubIndex` to `hands.length - 1` when the viewer is "following latest", specifically to cover the initial-load gap: `useHandPolling`'s `onAutoAdvance` is guarded by `prevCount > 0 && sorted.length > prevCount`, which skips the first fetch (because `prevCount === 0`). Without this effect, `scrubIndex` would remain at `-1` forever on fresh loads. The equality guard (`latest !== scrubIndex`) and the `isFollowingLatest` flag prevent loops. This is the textbook "external-source sync" exemption the `set-state-in-effect` rule calls out.
- **Recommended fix:** none required. A tighter refactor would push the first-load advance into `useHandPolling` itself (e.g. `onFirstLoad?` callback) and remove the effect entirely, but that is a hook-API change out of scope for T-032.

#### [L-2] AC-2 source-regex does not assert `isShowdown` absence

- **Description:** AC-2 wording: "Legacy `handToPlayerCardData` + direct `isShowdown` usage in this file are removed." The test regexes for `createPokerScene`, `handToPlayerCardData`, and `from '../scenes/showdown`, but not for the bare token `isShowdown`.
