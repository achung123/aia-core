## Findings

### MEDIUM

**M1 — Re-clicking "Cinematic" after interrupt is a silent no-op.**
File: [frontend/src/scenes3d/animations/cameraPresets.ts](frontend/src/scenes3d/animations/cameraPresets.ts#L128-L131)

After `interrupt()`, the machine holds `preset='cinematic'`, `cinematicActive=false`, `transition=null`. If the user clicks "Cinematic" again on the toolbar (the active-highlighted button, which is the most natural affordance), `setPreset('cinematic')` hits:

```ts
if (next === preset && transition === null) return;
```

…and exits without re-entering orbit. The user has no way to resume the orbit without round-tripping through a different preset. The design doc on line 13 states "yields permanently on user input," which is one valid reading of AC 3, but the toolbar leaves "Cinematic" highlighted-as-active so re-click looks like the obvious affordance.

**Recommendation:** Either (a) special-case the guard so a re-click on `cinematic` when `!cinematicActive && !reducedMotion && preset === 'cinematic'` re-invokes `beginCinematicOrbit()`, or (b) render the toolbar button with a visual "yielded" state and/or document the round-trip requirement. Option (a) preserves the current state-machine semantics for non-cinematic re-clicks while fixing the UX.

**M2 — useFrame mock inconsistent with the rest of the scenes3d suite.**
File: [frontend/test/scenes3d/CameraPresetController.test.tsx](frontend/test/scenes3d/CameraPresetController.test.tsx#L22-L29)

The new test replaces the registered callback on every render:

```ts
vi.mock('@react-three/fiber', () => ({
  useFrame: (cb) => {
    frameCallbacks.length = 0;
    frameCallbacks.push(cb);
  },
}));
```

Existing scenes3d tests (DealAnimationDriver, PokerTable) use append-only mocks. Real R3F registers per-fiber and unregisters on unmount (i.e., multi-instance and strict-mode-double-mount produce multiple live callbacks until cleanup runs). Replace-latest:

- Hides any `onInteract` closure-capture regression across re-renders (a stale callback staying registered is automatically overwritten);
- Hides cleanup bugs when the component unmounts;
- Cannot catch "callback still fires after unmount" scenarios since re-mount silently reuses one slot;
- Diverges from the suite convention, which makes cross-test debugging harder.

The tests as written pass under both conventions because they only mount a single controller with no unmount/remount. **This is currently safe** — but it's a sharp edge that will bite the first time someone adds a StrictMode or multi-controller test.

**Recommendation:** Align on append-only across the scenes3d suite, or expose a shared `clearFrameCallbacks()` helper in a test util. At minimum, add one explicit `unmount()` test asserting the callback list shrinks.

**M3 — `reducedMotion` captured at controller mount; OS-pref flips not tracked.**
File: [frontend/src/scenes3d/components/CameraPresetController.tsx](frontend/src/scenes3d/components/CameraPresetController.tsx#L43-L46)

`useReducedMotion()` is read during render and baked into the machine via the lazy ref init. Because `machineRef` is never rebuilt, toggling the OS `prefers-reduced-motion` flag after mount is silently ignored (machine still tweens or still orbits). Low-probability but real — users toggle system-level reduce-motion in Settings without reloading the page.

**Recommendation:** Add `machine.setReducedMotion(flag)` and forward it via a `useEffect([reducedMotion])`. Alternatively, re-key `<CameraPresetController key={reducedMotion ? 'rm' : 'full'}>` at the call site to recreate the machine; simpler but throws away orbit state.

**M4 — Toolbar is exported + tested but not mounted anywhere; API-drift risk before T-022/T-031 wire it.**
File: [frontend/src/scenes3d/components/CameraPresetToolbar.tsx](frontend/src/scenes3d/components/CameraPresetToolbar.tsx)

`<CameraPresetToolbar>` has zero production consumers. `PokerTable.onPresetChange` is explicitly disabled (`eslint-disable @typescript-eslint/no-unused-vars`). Hank's notes confirm this is intentional (T-031 PlaybackView / T-022 seat-POV will wire it), but the component ships with a frozen API while its likely consumers haven't been designed yet:

- No "yielded" indicator for M1's UX gap;
- No disabled/loading state;
- `hidden` is a boolean but T-022 player-mode might need a granular "cinematic-only-hidden";
- Controlled-only (no uncontrolled variant).

**Recommendation:** File a bd follow-up under T-031/T-022 blocking: "Re-review `CameraPresetToolbarProps` before wire-up — ensure M1 cinematic-yielded state is representable." This prevents toolbar API from locking in before its first real integration.

### LOW

**L1 — Seat-POV silent fallback.** [frontend/src/scenes3d/PokerTable.tsx](frontend/src/scenes3d/PokerTable.tsx#L92-L95) maps `{kind:'seat'}` → `'default'` with no signal. If a caller wires seat preset before T-022 ships, the camera silently lands on default. Consider a dev-only `console.warn` for unhandled preset kinds.

**L2 — Unnecessary happy-dom env.** [frontend/test/scenes3d/cameraPresets.test.ts](frontend/test/scenes3d/cameraPresets.test.ts#L1) declares `@vitest-environment happy-dom` but the file exercises pure state-machine logic only. `node` environment would be slightly faster.

**L3 — No explicit StrictMode test for the controller.** [frontend/test/scenes3d/CameraPresetController.test.tsx](frontend/test/scenes3d/CameraPresetController.test.tsx) does not wrap any render in `<StrictMode>`, unlike the Cycle 11 regression added for `PokerTable.onReady`. The ref-held machine + single-shot useFrame makes this component a plausible candidate for the same class of bug. The existing Cycle 11 follow-up ("suite-wide StrictMode test strategy") would subsume this if picked up.

**L4 — `onInteract` prop name is broader than its semantic.** [frontend/src/scenes3d/components/CameraPresetController.tsx](frontend/src/scenes3d/components/CameraPresetController.tsx#L20) fires only when transitioning cinematic → yielded, not on every user drag. Consider renaming to `onCinematicYield` before any external consumer lands.

**L5 — Per-frame 6-value pose equality in `setPose`.** [frontend/src/scenes3d/components/CameraPresetController.tsx](frontend/src/scenes3d/components/CameraPresetController.tsx#L66-L82) does a six-scalar comparison each frame. Negligible cost but trivially replaceable with a version counter on the machine or `Object.is` on the returned array reference (the machine currently allocates new arrays only when pose changes). Micro-perf; defer.
