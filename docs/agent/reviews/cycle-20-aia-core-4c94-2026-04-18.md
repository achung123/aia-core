## Findings

### [MEDIUM] M-1 — Cancel-on-scope-change UX: mid-flight slugs vanish when street advances

**File:** `frontend/src/scenes3d/animations/ChipSlideController.ts`
**Line(s):** 101-114
**Category:** design

**Problem:**
Option B (cancel-on-scope-change) was chosen to keep the `committedThisStreet − inFlight` invariant non-negative. Correct and defensible — but the visual consequence is that a mid-flight chip slug is abruptly removed from the scene, while `state.pot` jumps by the cancelled delta in the same frame (backend absorbs `committedThisStreet` into `pot` at street boundary). For a 400 ms tween that transitions at t ≈ 200 ms, the user sees: "chips in the air" → *snap* → "chips teleported to pot, half the flight distance skipped."

This is a rare edge (players normally pause between streets), but in fast-dealt replays or reduced-motion contexts it becomes visible.

**Code:**
```ts
if (this.seqScope !== null && this.seqScope !== scope) {
  for (const tween of this.active.values()) tween.cancel();
  this.active.clear();
  this.inFlight.clear();
}
```

**Suggested Fix:**
Defer the bookkeeping reset: on scope change, let the existing tweens finish (≤ 400 ms remaining), keep `inFlight` bookkeeping alive until they do, and only then clear. Consumer-side invariant still holds because `state.pot` after the street transition already includes the delta, so `pot_display = state.pot + Σdeposited` will temporarily over-count by the in-flight amount — which is exactly the visual we want (pot still growing as each slug lands). Alternative: tween the slug directly to `POT_CHIP_WORLD_POSITION` in the remaining budget.

**Impact:** Low in normal play; visible in fast-forward replay / reduced-motion.

### [MEDIUM] M-2 — `bumpFrameTick` triggers full `<PokerTable>` re-render every frame while any slide is active

**File:** `frontend/src/scenes3d/PokerTable.tsx`
**Line(s):** 221, 393, 449
**Category:** design / performance

**Problem:**
`FlyingChipSlug` already `setPos`es on its own state per frame to move its position — that alone is sufficient to re-render *the slug*. The additional `onFrameTick` call invokes a `useReducer` dispatch on the parent `<PokerTable>`, causing the whole scene subtree (seats, community cards, chip stacks, nameplates, dealer markers) to re-render at 60 Hz for the duration of every chip slide.

`inFlightForSeat(seatIndex)` and `depositedTotal` are the only parent-scope values that depend on controller state, and both change only on `onSlideStart` / `onSlideComplete` — both of which already `setActiveSlides` / `setDepositedBySeat`, which already re-render the parent. There is no value the parent derives that changes *per frame* during a slide.

**Code:**
```tsx
const [, bumpFrameTick] = useReducer((x: number) => (x + 1) & 0xffff, 0);
// …
<FlyingChipSlug … onFrameTick={bumpFrameTick} />
// inside FlyingChipSlug:
setPos(…);
onFrameTick();
```

**Suggested Fix:**
Delete `bumpFrameTick` and `onFrameTick`. `FlyingChipSlug`'s local `setPos` is the correct (and only needed) re-render boundary. This reduces render work during a 400 ms slide from ~24 full-scene renders to 1 start + 1 complete.

**Impact:** Measurable render cost at 10 seats × 2 concurrent slides; matters more for T-012 pot-sweep which will have 1 × N winner slugs in flight simultaneously.

### [LOW] L-1 — One-frame "unshrunk" seat stack before the effect flushes

**File:** `frontend/src/scenes3d/animations/ChipSlideDriver.tsx`
**Line(s):** 124-126
**Category:** design

**Problem:**
`<ChipSlideDriver>` syncs in a `useEffect` on `[state, layout]`. On the render pass that first introduces a bet, the parent renders *before* `sync` runs, so for one commit cycle `inFlightForSeat` returns 0 and the seat's committed stack briefly shows full amount. Tests pass because RTL's `rerender` awaits effect flush before the probe is read; in a real browser this is one ≤ 16 ms frame.

**Suggested Fix:**
Switch `<ChipSlideDriver>`'s sync effect to `useLayoutEffect`, or — more surgically — expose a synchronous shadow `inFlightByKey` map written *before* `onSlideStart` fires, so render-site `display` math is consistent within the same commit as the state change.

**Impact:** Visually imperceptible at 60 Hz; worth noting because T-012 pot-sweep and T-013 showdown will stack on the same primitive.

### [LOW] L-2 — `__getTestProbe().getStacks()` is an observable boundary, not a backchannel, but should be labelled as such

**File:** `frontend/src/scenes3d/components/ChipInstances.tsx`
**Line(s):** 108-143, 262-270
**Category:** convention

**Problem:**
The reviewer asked (focus e) whether `getStacks()` leaks implementation detail. Verdict: **legitimate observable boundary.** The probe returns the *same* `stacksRef.current` Map that `flush()` iterates to write every InstancedMesh matrix — i.e. what renders is a pure function of this registry, so asserting on the registry *is* asserting on what renders, minus only the GPU decomposition (`chipCountsFor`) which is separately unit-tested. happy-dom has no WebGL; there is no lower-level surface available in jsdom/vitest.

That said, the JSDoc frames it as a test probe rather than as the canonical scene-graph observation API, and the `__` prefix + `__getTestProbe` naming reinforces "backdoor" vibes. Future readers may incorrectly gate tests on InstancedMesh matrix reads.

**Suggested Fix:**
Add one line to the JSDoc making the architectural claim explicit: "`getStacks()` returns the authoritative pre-GPU registry — assertions on this snapshot are equivalent to assertions on rendered chip positions modulo `chipCountsFor`." No code change required.

**Impact:** Test-strategy clarity.

### [LOW] L-3 — `handleController` is stable but the driver's `onController` fires twice under StrictMode

**File:** `frontend/src/scenes3d/animations/ChipSlideDriver.tsx` · `frontend/src/scenes3d/PokerTable.tsx`
**Line(s):** Driver 104-123; PokerTable 238-240
**Category:** correctness

**Problem:**
Under StrictMode (dev) the mount-only effect fires → cleanup fires (`c.reset()`, `controllerRef = null`) → mount fires again with a new `c`. Parent's `handleController` stashes into a `useRef` (per Cycle 19 L-2 guidance), so the second call correctly overwrites the stale ref. Verified by reading code.

However: between cleanup and second mount, if any frame/layout work reads `controllerRef.current` it will see the *first* (reset-but-still-retained-by-parent) controller — not null. `reset()` clears in-flight state so `getInFlightAmountForSeat` returns 0 and `getInFlightPosition` returns null, which is safe. No observable bug. But there is no test that asserts this — a StrictMode-wrapped render of `<PokerTable>` with immediate state diff would pin the invariant.

**Suggested Fix:**
Add a single StrictMode wrapper test in `PokerTable.test.tsx` (analogous to the Cycle 11 `onReady` test): render under `<React.StrictMode>`, drive a bet, assert the slide completes and pot grows by exactly the delta once.

**Impact:** Regression risk if the controller wiring changes; currently benign.

### [LOW] L-4 — `inFlightForSeat` is an inline closure called from render

**File:** `frontend/src/scenes3d/PokerTable.tsx`
**Line(s):** 280-282, 362
**Category:** convention

**Problem:**
`inFlightForSeat` is defined as a plain function inside the component body and invoked once per seat inside the render JSX. `controllerRef.current?.getInFlightAmountForSeat(i)` iterates the controller's `inFlight` map each call — O(active-slides) per seat per render. At 10 seats × ≤ 20 active slides this is trivial, but it's a non-memoised hot path.

**Suggested Fix:**
Compute a `Map<seatIndex, number>` once per render from `controllerRef.current?.getInFlightByAllSeats()` (new controller method), or memoize via `useMemo([activeSlides])`. Not urgent.

**Impact:** Imperceptible at current seat/slide counts; informational.
